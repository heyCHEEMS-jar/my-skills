# 风格示例与边界

以下是原创教学示例，不代表真实开发经历。示例中的假设只对这个例子有效。

## 1. 从模板腔变成具体问题

假设材料已确认：提交业务函数稳定存在，冷却期内直接返回，表单默认行为未在外层阻止。不要据此推断真实项目使用哪个节流库。

### 不推荐

> 在现代前端开发中，表单交互是不可或缺的一环。本文将深入探讨 React 与节流函数结合使用时可能产生的复杂问题，并提供全面而高效的解决方案。

问题：没有说明具体异常，先给空泛背景；“全面而高效”也没有证据。

### 推荐的中性初稿

````markdown
# 为什么给表单提交加了节流，重复点击还是会刷新页面？

给登录表单加节流，本来是想防止重复提交。但如果把阻止默认提交的逻辑也放在业务回调里，被拦截的点击反而可能触发表单默认行为。

下面只看一个简化场景：节流函数在冷却期内直接返回。

```jsx
const handleSubmit = e => {
  e.preventDefault()
  submitLogin()
}

const throttledSubmit = throttle(handleSubmit, 2000)

// 表单中
<form onSubmit={throttledSubmit}>
  <button type="submit">登录</button>
</form>
```

这里的 `submitLogin` 和 `throttle` 是已有的业务函数与节流工具，代码只展示和事件顺序有关的部分。

问题在哪？

第一次提交会进入 `handleSubmit`，所以 `preventDefault` 能执行。

但冷却期内的第二次提交被节流挡住了，`handleSubmit` 没有执行，`preventDefault` 也就没机会执行。

```text
第二次提交 → 节流直接返回 → 没有阻止默认行为 → 浏览器继续默认提交
```

节流应该限制业务请求，不应该连表单事件的默认行为处理一起跳过。

把 `preventDefault` 放到节流外面：

```jsx
<form onSubmit={e => {
  e.preventDefault()
  throttledSubmit(e)
}}>
  <button type="submit">登录</button>
</form>
```

这样每次提交事件都会先阻止默认行为，再判断是否执行节流后的业务。修复后可以在冷却期内连续点击，检查页面是否导航，以及业务请求次数是否符合节流预期。
````

特点：没有替用户写“我排查了一下午”；只讲被跳过的动作，不把问题笼统归结成“React 缓存冲突”；给的是验证步骤，不是假装验证结果。

## 3. 不把怀疑写成根因

### 不推荐

> 原生组件不重新测量 inline-block，所以浏览器肯定跳过了脏节点检查，给 height 就能解决所有平台的高度坍塌。

> 先在问题发生时查看容器的实际高度，以及父级有没有尺寸约束。如果还要解释到底是哪一层没有重新布局，需要补上运行平台、UniApp 版本和最小复现。

## 4. 速查条目的克制写法

````markdown
## docker logs — 查看容器日志

```bash
docker logs -f --tail 100 <container>
```

把 `<container>` 换成容器名或 ID。`--tail 100` 先取最后 100 行，`-f` 继续跟踪新输出。
````

这个条目不需要“背景介绍—底层原理—性能优化—总结”。如果条目变成删除容器、删除 volume 或清空文件，则必须说明影响，不省略关键安全边界。

## 5. 结束在哪

- 小修复：停在“改动改变了什么”或验证步骤。
- 临时补丁：停在“安装依赖可能覆盖这处修改”的提醒。
- 手写代码：停在一个关键限制或使用方式。
- 多坑长文：必要时归纳两三点，不升华成普遍成功学。

新写文章不固定追加“持续收集中...”或“更新于……”。这些是特定合集/更新场景的表达，只有确有对应需求才使用。

## 6. 格式完整，仍然不像作者

假设作者提供了这些材料：开发插件编译推送模块，需要比较几种编译器；必须输出 CommonJS；原生方案的多平台依赖让 VSIX 达到 76 MB；改用 WASM 后为 7.98 MB。下面是原创写作示例，不代表对具体工具做过测试。

### 不推荐

> 这次选型大致经历了三个阶段。首先对比各候选方案，其次分析功能约束，最后解决跨平台交付问题。
>
> 这次经历让我重新理解了技术选型的本质。我放下了对单一性能指标的执着，选择了一条能把功能可靠送到用户手里的路。

问题：开头预告了读者马上会看到的结构，结尾又把已知过程换成抽象概念，还擅自补了作者心理。

### 更直接的写法

> 写插件的编译推送模块时，需要把 TypeScript、JSX 等代码转换成平台要求的 CommonJS，所以对比了几种编译器。
>
> ## 方案 A
>
> 方案 A 的转换速度很快，但当时使用的版本不能输出 CommonJS。虽说可以再接一层工具处理模块格式，但会增加依赖和验证成本，为了这一点速度把转换拆成两段，没这个必要。
>
> ## 原生方案 B
>
> 方案 B 能满足转换要求，问题是原生绑定需要区分操作系统和 CPU 架构。把多平台依赖一起打进通用安装包后，整个 VSIX 达到了 76 MB。
>
> ## WASM 方案
>
> 换成 WASM 后不用再分别携带几套平台绑定，最终 VSIX 降到了 7.98 MB。这个功能一次只转换少量文件，当前更看重安装包体积和跨平台交付。

这类文章不需要为了技术感补实现代码，也不必再加候选方案总表和总结。小标题直接用方案名即可；完整因果可以写在同一段，不必刻意拆成连续短句。

### 数据也按博客语气写

材料里已经有性能比较时，直接写对当前选型有用的结论：

> 方案 A 的转换速度比方案 B 快数倍，但这次最终卡住的是模块格式，不是速度。

数据拿不准时，先在协作阶段问作者；确认后直接写进正文，不展开自己查数据的过程。个人博客要把事情讲明白，不需要给每个判断补一段说明。

时间与版本边界也放在事实旁：

> 当时使用的方案不支持 CommonJS。

一句已经说清，就不再另起一段声明“并非永远不支持”。必要限定要保留，但它只负责防止误解，不负责展示文章有多严谨。
