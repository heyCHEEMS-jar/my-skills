# 文章骨架

这些是起草时的可选结构，不是必须逐格填写的表单。先确定事情和疑问的顺序，再按需借用骨架；不要先列齐栏目，再往里面填素材。小节标题写具体问题，不照搬“背景—挑战—决策—启示”。

下列外层四反引号用于展示 Markdown 源码；实际交付默认直接输出文章，不保留外层围栏。方括号是模板提示，不能原样作为正文事实。没有用户经历时用中性示例；没有根因时不要在标题中断言根因。

## 1. 踩坑复盘

适用：用户有具体异常和排查材料。很短的问题可去掉全部小标题。

````markdown
# [技术/场景] 下 [具体异常] 的问题

[具体场景、想实现什么。]

[原本以为正常的逻辑、实际出现的结果。只用提供的事实。]

## 问题代码

[说明这段是原始片段还是简化演示，以及看哪里。]

```js
// 与问题直接相关的片段
```

## 原因分析

[直接解释关键机制；原因未确认时改为“先检查哪里”，或留下具体待补注释。]

[确实有时序差异时，再列一次关键过程。]

```text
触发条件 → 状态检查 → 执行/跳过 → 实际结果
```

## 解决办法

[改哪里，为什么。只有有依据的修复才写成解决办法，否则写排查方向。]

```js
// 对应的局部修改
```

[实际已验证的结果，或验证步骤及预期。必要时补一条平台/版本边界。]
````

多坑文章可以用 `## [坑一的具体现象]`、`## [坑二的具体现象]`，每节内部直接写原因、代码和修复，不强行给每个坑重复三级结构。

## 2. 快速上手

适用：安装、工具接入、配置方案。只保留影响成功的前提，不扩写成环境配置大全。

````markdown
# 如何用 [工具] 实现 [目标]？

[一句说明为什么需要，以及最小方案。]

## [安装或接入]

[只列确实需要的前提和步骤；有已核实命令时再给代码块。]

## [配置]

[只解释影响成功的配置；多个配置需要对照时再用表格。]

## [验证]

[需要读者确认结果时，给具体操作与预期。没有实际执行过，不写“验证成功”。]
````

流程图、准备小节、权限提醒、平台边界都按材料需要增加，不把每一项当成固定栏目。Windows 专用命令改用 `powershell`，不能把 Bash 语法当成 PowerShell。

## 3. 手写实现

适用：函数、类或小算法。完整实现可以先贴；很长的实现拆成有意义的片段。

````markdown
# 简单实现一个 [目标]

[一句目的，或“先上一个简化实现：”。]

```js
// 教学实现；明确边界，不伪装成生产级完整替代
```

## 为什么要 [关键状态/数组/数据结构]？

[解释最容易不理解的一点。]

[小例子或执行顺序，不逐行复述代码。]

## [另一个真正的难点，可选]

[异步、引用身份、边界条件等。]

[必要的使用示例和简化范围；讲完就停。]
````

不足两个难点时，不强行补两个标题。非代码改动请求中，不借写文章擅自重构用户的项目代码。

## 4. 命令/算法速查

适用：多个独立条目。不编造更新日期，不套开发经历。

````markdown
# [技术] 常用 [命令/模板]

## [条目一] — [用途]

[必要前提；尤其是算法适用条件和破坏性命令。]

```bash
# 命令或代码
```

[确有多个选项才用表格，否则一句解释即可。]

## [条目二] — [用途]

```bash
# 命令或代码
```

[限制、常见陷阱或使用提醒。]
````

算法围栏用实际语言，输入与返回含义明确。涉及删除文件、删除数据、清空缓存、强制杀进程或覆盖部署时，先写清作用范围与不可逆影响，不把“常用”当作安全保证。

## 5. 概念解释

适用：主题明确但没有开发经历，或用户要讲清一个机制。

````markdown
# 什么是 [概念]？

[一句白话定义，随后补当前问题需要的准确边界。]

## [最值得解释的机制或区别]

[用最小场景说明；确实依赖执行顺序时再加文字流程，需要比较多个概念时再增加小节或表格。]

[讲到读者能理解当前概念即可；有关键限制时用一句收尾。]
````

## 6. 选型经历

适用：作者提供需求、候选方案、遇到的限制和最后结果。先找出硬性要求，再决定按换方案的时间顺序写，还是按候选方案分别写；哪种更接近作者现有文章就用哪种，不预先安排“认知升级”或工程感悟。

````markdown
# [功能] 的 [工具/方案] 选型

[一句说明正在做什么，以及最终输出必须满足什么。]

## [候选方案 A]

[能力是否满足、为什么考虑或排除。只写影响选择的差异。]

## [候选方案 B]

[性能、生态、运行方式或交付成本中的关键取舍。材料里有比较数据就自然写进去。]

## [最终方案]

[为什么满足当前场景，接受了什么代价，以及实际结果。]
````

如果文章重点是连续换方案，也可以沿着实际过程写：

```text
必须满足的能力 → 第一方案缺少什么 → 第二方案带来什么交付问题 → 最终方案和结果
```

没有关键实现差异时不贴代码；没有必要逐项比较时不做总表；用户未要求资料时不自动附参考资料节。结尾通常停在最终方案的取舍和结果，不再重复整条链路。

## 标题与 frontmatter

- 独立 Markdown 默认一个 `# 标题`。
- 用户提供原始博客模板/源文件时，按真实字段输出，标题不要同时重复在 frontmatter 与正文。
- 未获得真实 schema 时不自动附 `published`、`updated`、`category`、`tags`、`image`、`draft` 等字段。
- 发布信息未提供就省略或询问，不能默认今天发布。

## 信息不足时

优先写已知部分；局部缺项用例如 `<!-- 待补：触发异常的平台、框架版本与完整报错 -->`。只有根因缺失时，保留现象，把“原因分析”改为“先检查哪里”。大部分正文都缺失时，只给最小骨架，不把占位符堆成貌似完整的文章。
