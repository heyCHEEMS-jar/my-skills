# 写作风格要点

## 先看作者怎么说话

用户提供博客或样文时，先读几篇与当前题材接近的正文，不只看页面布局。比较开头如何进入问题、句子如何衔接、解释在哪里展开、讲到哪里停止；记录少量实际措辞作为当前写作依据，不把分析塞进文章。

格式相同不代表声音相同。标题、短段和代码块都对了，仍可能因为预告提纲、反复总结和金句而像标准化复盘。作者参考只校准表达，不能证明其中的技术解释正确。

## 核心节奏

像开发者给自己和同类读者整理技术笔记：这次遇到了什么，为什么会这样，最后怎么改，而不是替技术做宣传。

1. 直接说具体情况。
2. 先让读者看到反直觉结果或关键代码。
3. 顺着疑问解释。
4. 用状态、执行顺序、平台差异或代码对照建立因果。
5. 修复与边界讲完就停。

速查和手写实现可以直接进入条目或代码，不强行套入排查过程。

## 标题与开头

- 标题突出技术场景、具体问题或实现目标，不靠营销形容词。
- 因果是重点时用“为什么”，操作是重点时用“如何”，修复明确时直接写问题和版本。
- 场景复盘用 1–3 个短段交代目标、实现与异常，不先铺行业背景。
- 手写实现可以一句目的后直接给代码；概念解释可以从最小定义开始。
- 没有真实经历时用中性场景，不虚构项目、排查过程或第一人称测试记录。

## 语气与段落

- 一段讲一个关系，通常 1–3 句。
- 自然转折、适度口语，但不靠固定口头禅或强情绪塑造人设。“想着……但实际……”适合交代预期和结果，“这里其实是……”适合纠正理解；过渡必须有具体内容，不能只是套词。
- 从白话推进到准确术语，再回到当前问题，不一口气堆定义。
- 问句只在确实有疑问需要展开时使用，不把每段都写成问答。
- 安装步骤和执行顺序可以编号；普通叙述不必反复使用“首先、其次、最后”。
- 第一人称用来说明做了什么、试了什么，不擅自补“重新理解了”“放下执着”“改变优先级”等心路历程。
- 少用成对的“不是……而是……”强调结论，不把同一事实换几个抽象词重复说。

## 解释方式

- 时序问题拆开关键动作，让读者知道哪一步没执行、晚执行或被覆盖。
- 状态问题说清状态存在哪里、何时改变、谁读取，不笼统归结为“缓存冲突”。
- 平台差异明确区分运行端、编译器和版本，不把单个平台的现象推广为通用规律。
- 类比后回到机制，指出对应的节点、槽位、缓存或回调。
- 简单流程用箭头链，复杂关系才用 Mermaid，不重复放等价图。

## 代码与 Markdown

- 只贴影响结论的片段，保留问题代码与修复代码之间有用的差异。
- 代码前说明看哪里，代码后解释改动为什么改变行为，不逐行翻译。
- 区分原始片段、简化演示、局部修复和可运行示例。
- 独立草稿默认一个 H1，正文用 H2/H3；小问题可以没有正文小标题。
- 少量加粗强调关键限制，表格用于参数或对应关系，不把普通叙述硬塞进表格。
- 默认用空行分段，不加主题专用布局、装饰容器或虚构截图。
- frontmatter 由用户提供的格式决定，不猜日期、封面、分类或 slug。

## 文体与收尾

| 文体 | 展开方式 |
| --- | --- |
| 单点踩坑 | 现象、关键片段、原因、修复，讲完就停 |
| 多坑实践 | 按问题分节，必要时先交代实现思路 |
| 选型经历 | 需求、实际选择、遇到的限制、替换方案、结果；不包装心路历程 |
| 快速上手 | 目的、必要步骤、配置、验证 |
| 手写实现 | 代码先行，解释关键状态与难点 |
| 速查合集 | 小标题、代码或命令、前提与参数 |
| 概念解释 | 最小定义、例子、运行过程、边界 |

篇幅由问题复杂度决定，不为凑字数补背景、百科知识或总结。小修复停在改动或验证步骤；临时补丁补充覆盖风险；长文确有必要时才简短归纳。

## 事实边界

表达风格不替代技术验证。把用户确认的观察、可核实的机制和待验证的解释分开，不虚构版本、经历、测试结果或性能数字。

用户提供的文章只用于提炼写作规则，不把原文、文章清单或站点信息收录进 Skill；需要示例时另写中性教学材料。
