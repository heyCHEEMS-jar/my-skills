# 风格示例与边界

以下是原创教学示例，不代表真实开发经历。示例中的假设只对这个例子有效。

## 1. 从模板腔变成具体问题

假设材料已确认：提交业务函数稳定存在，冷却期内直接返回，表单默认行为未在外层阻止。不要据此推断真实项目使用哪个节流库。

### 不推荐

> 在现代前端开发中，表单交互是不可或缺的一环。本文将深入探讨 React 与节流函数结合使用时可能产生的复杂问题，并提供全面而高效的解决方案。

问题：没有说明具体异常，先给空泛背景；“全面而高效”也没有证据。

### 推荐的中性初稿

````markdown
# 为什么给表单提交加了节流，重复点击还是会刷新页面？

给登录表单加节流，本来是想防止重复提交。但如果把阻止默认提交的逻辑也放在业务回调里，被拦截的点击反而可能触发表单默认行为。

下面只看一个简化场景：节流函数在冷却期内直接返回。

```jsx
const handleSubmit = e => {
  e.preventDefault()
  submitLogin()
}

const throttledSubmit = throttle(handleSubmit, 2000)

// 表单中
<form onSubmit={throttledSubmit}>
  <button type="submit">登录</button>
</form>
```

这里的 `submitLogin` 和 `throttle` 是已有的业务函数与节流工具，代码只展示和事件顺序有关的部分。

问题在哪？

第一次提交会进入 `handleSubmit`，所以 `preventDefault` 能执行。

但冷却期内的第二次提交被节流挡住了，`handleSubmit` 没有执行，`preventDefault` 也就没机会执行。

```text
第二次提交 → 节流直接返回 → 没有阻止默认行为 → 浏览器继续默认提交
```

节流应该限制业务请求，不应该连表单事件的默认行为处理一起跳过。

把 `preventDefault` 放到节流外面：

```jsx
<form onSubmit={e => {
  e.preventDefault()
  throttledSubmit(e)
}}>
  <button type="submit">登录</button>
</form>
```

这样每次提交事件都会先阻止默认行为，再判断是否执行节流后的业务。修复后可以在冷却期内连续点击，检查页面是否导航，以及业务请求次数是否符合节流预期。

这里没有讨论节流实例在组件重渲染时如何保持稳定；如果实例本身会重建，还需要另行检查它的创建位置与依赖。
````

特点：没有替用户写“我排查了一下午”；只讲被跳过的动作，不把问题笼统归结成“React 缓存冲突”；给的是验证步骤，不是假装验证结果。

## 4. 速查条目的克制写法

````markdown
## docker logs — 查看容器日志

```bash
docker logs -f --tail 100 <container>
```

把 `<container>` 换成容器名或 ID。`--tail 100` 先取最后 100 行，`-f` 继续跟踪新输出。
````

这个条目不需要“背景介绍—底层原理—性能优化—总结”。如果条目变成删除容器、删除 volume 或清空文件，则必须说明影响，不省略关键安全边界。

## 5. 结束在哪

- 小修复：停在“改动改变了什么”或验证步骤。
- 临时补丁：停在“安装依赖可能覆盖这处修改”的提醒。
- 手写代码：停在一个关键限制或使用方式。
- 多坑长文：必要时归纳两三点，不升华成普遍成功学。

新写文章不固定追加“持续收集中...”或“更新于……”。这些是特定合集/更新场景的表达，只有确有对应需求才使用。

### 限定语放在相关事实旁

这句话已经限定了时间和方案，不必再加一段“并非断言永远不支持”。未提供跑分时不编精确差距；只有确需澄清时补一句“没有做两种方案的耗时对比”，不用每节重复自证。若材料不足以支持技术判断，仍应保留必要的不确定性，不能为了口语顺滑删掉。
