# 软件工程面试追问路线

这是一张出题地图，不是每场面试都要跑完的题库。技术知识只确认基础门槛，主要观察候选人怎样思考、决策和验证。先从候选人的真实主张进入，再选择最能区分目标级别的路线。每次只改变一个主要变量。

## 通用思维链探测

面对项目、编码、调试或设计问题，都优先沿同一条思维链取证：

1. **定义**：你认为真正的问题是什么？目标用户、成功标准和不做什么分别是什么？
2. **未知**：当前还缺哪些信息？哪些是假设，哪些是已知事实？
3. **约束**：什么业务、数据、时序、资源、安全、成本或期限会改变方案？
4. **拆解**：你会把问题分成哪些可独立理解或验证的部分？先处理哪一部分，为什么？
5. **假设**：有哪些可能原因或解释？如何排序？哪项观察最能区分它们？
6. **方案**：有哪些现实选择？每个方案依赖什么前提，最大代价是什么？
7. **选型**：为什么选这个？为什么不用另一个看似合理的方案？什么变化会让你改选？
8. **量化**：基线、指标、样本、实验和成功阈值是什么？如何排除其他变量？
9. **修正**：如果观察结果与预期相反，你会撤回哪项判断，下一步验证什么？
10. **闭环**：如何实现、测试、发布、观测、恢复，并判断业务结果？

不要一次问完十项。根据当前回答缺失的关键一环，每轮只追一个问题。候选人能背出术语但不能走通这条思维链，只算基础知识过关；能在陌生场景中形成并修正这条链，才是高价值能力证据。

## 选型深挖

候选人说“选择了某框架、数据库、协议或架构”时，不要停在优缺点背诵：

- 当时必须满足的约束和优先级是什么；
- 进入候选集的现实方案有哪些，为什么是它们；
- 用了哪些评价维度，是否有权重冲突；
- 淘汰其他方案的证据是什么，而不是事后合理化；
- 是否做过原型、压测、迁移试验或成本估算；
- 当前方案最贵的代价和最先失效的条件是什么；
- 哪个指标或事件会触发重新选型。

合理选型不要求唯一答案，要求决策过程能被约束和证据解释。

## 量化与验证

任何“提升、降低、稳定、可扩展、安全”的结论都追到：

- 优化对象和用户可见目标；
- 优化前基线与测试环境；
- 指标定义、统计口径和成功阈值；
- 对照组、样本量、重复次数和方差；
- 如何隔离其他变化并建立因果归因；
- 收益是否以另一项成本为代价；
- 上线后怎样观测，失败怎样回滚。

当候选人无法给出历史数据时，不要求编造数字；观察他能否承认证据边界，并设计现在可执行的验证方案。

## 通用项目深挖

按信息增益选问题：

1. **背景**：谁遇到了什么问题？不做会有什么影响？
2. **责任**：你亲自决定、实现和验证了什么？哪些来自团队、库或 AI？
3. **建模**：核心实体、状态、数据结构、接口或事件是什么？
4. **执行**：拿一个真实样例走完端到端过程。
5. **机制**：方案成立依赖哪些不变量、平台行为或协议保证？
6. **边界**：改变数据量、时序、失败模式、权限或兼容条件后怎样？
7. **取舍**：至少一个现实替代方案为何没选？成本分别是什么？
8. **证据**：基线、指标、环境、测量方法和回归结果是什么？
9. **复盘**：现在重做会保留和改变什么？
10. **迁移**：把同一模型应用到邻近但不同的场景。

候选人说出“优化、重构、稳定、安全、可扩展、主导、从零搭建、支持大量用户”时，优先进入证据和责任链。

## 需求与业务理解

从一句不完整需求开始，观察候选人是否主动澄清：

- 用户与角色、目标和不做什么；
- 核心流程、状态和权限；
- 异常、空态、重复操作和恢复；
- 验收标准、优先级、期限与依赖；
- 埋点、反馈与业务成功指标。

升压方式：加入角色冲突、规则变化、期限不变、历史数据兼容或灰度发布。不要期待候选人猜中隐藏需求；评价的是发现未知和收敛决策的能力。

## 编码与数据结构

基础观察点：

- 是否先确认输入、输出、错误和边界；
- 是否提出不变量并选择匹配的数据结构；
- 是否写出可读、可运行的最小实现；
- 是否主动走样例、分析复杂度和补测试。

逐级变量：

1. 基本功能与清晰接口；
2. 空输入、重复值、非法操作；
3. 状态历史、并发或异步；
4. 数据量和内存约束；
5. 持久化、恢复、幂等或分布式条件；
6. API 演进和调用方兼容。

候选人写完后先让他自己测试，再给一个反例。不要在编码过程中逐行暗示。

## 限时手撕算法路线

标准综合面至少安排一题，按岗位和前序表现控制难度：校招/初级以常见中等题检验基本功，中高级仍用可解释的算法与数据结构题，但通过工程约束和变体提高区分度，不转向竞赛偏题。

完整观察顺序：

1. **读题与澄清**：是否确认输入输出、数据范围、重复值、空值、顺序、可变性和错误语义。
2. **基础方案**：是否能先给出正确但可能不优的方案，说明瓶颈，而不是沉默寻找最优模板。
3. **关键思路**：能否说清不变量、数据结构选择、正确性理由和复杂度目标。
4. **完整编码**：是否写出可运行实现，命名、边界和控制流是否清楚。
5. **主动自测**：是否覆盖正常、边界、极值和反例，并手推关键状态。
6. **定位修正**：失败后是否根据现象缩小范围，而不是盲目改代码。
7. **复杂度**：能否推导时间、空间和最坏情况，而不是背结论。
8. **变体迁移**：只改变一个约束，观察能否复用底层模型并说明哪些部分必须重构。

题型可选：数组与字符串、哈希、双指针、滑动窗口、栈队列、链表、树图遍历、二分、堆、区间、回溯、基础动态规划。避免需要冷门定理、复杂数学技巧或固定题库记忆才能完成的题。

常见变体：

- 数据流式到达，不能一次读入内存；
- 输入规模扩大，原复杂度不可接受；
- 存在重复值或要求稳定顺序；
- 从返回一个解改为所有解或在线查询；
- 内存受限，要求原地修改；
- 增加并发访问、取消或错误恢复；
- 从一次性函数演进成可复用 API。

评价时区分：独立建模但有实现疏漏、思路依赖关键提示、代码正确但无法解释、会背模板却不能做变体、未完成但能提出可靠验证路径。AC 只是证据之一。

## 调试与故障处理

给“现象 + 环境 + 已知变化”，暂不公布原因。要求候选人依次说明：

1. 如何稳定复现并界定影响；
2. 当前最可能的 2–3 个假设；
3. 哪个日志、指标、抓包、快照或最小实验能区分假设；
4. 根据返回的观察更新概率，而非固守首个猜测；
5. 如何止损、修复、验证和防复发。

升压方式：只在候选人请求对应信息时释放结果；加入间歇复现、跨层依赖、最近发布、缓存、时序或环境差异。重点评分可证伪假设和证据闭环，不评分“猜中隐藏答案”的速度。

## 性能

追问链：

- 用户可见症状和业务目标是什么；
- 基线在哪个设备、数据量、网络和版本测得；
- 指标是延迟分位数、吞吐、帧率、内存、包体、CPU、成本还是错误率；
- 用什么 profile 或实验定位瓶颈；
- 改动影响关键路径的哪一段；
- 收益、方差、回归和后续监控是什么。

升压变量：冷/热启动、首屏/后续路径、典型/长尾设备、固定/动态数据、本地/网络瓶颈、多租户和成本上限。没有测量的“提升”只能算假设。

## 前端与客户端

可从真实项目选择：

- 渲染和更新：状态所有权、调度、布局绘制、长任务和内存；
- 复杂交互：焦点、键盘、点击外部、可访问性、受控状态；
- 长列表/画布：可见区、动态尺寸、定位、滚动锚定、二维空间；
- 网络与缓存：取消、去重、竞态、失效、离线、重试和错误态；
- 工程化：构建产物、代码分割、版本兼容、组件 API 和发布治理；
- SSR/多端：运行环境、同构边界、 hydration、平台能力差异；
- 安全：XSS、CSRF、令牌、第三方内容、文件和路径边界。

不要只问框架 API。要求候选人走事件时序、数据流、渲染成本或浏览器/运行时机制。

## 后端与分布式系统

可从真实服务选择：

- API 契约、鉴权、幂等、分页和版本演进；
- 数据模型、索引、事务、隔离级别和迁移；
- 缓存一致性、穿透、击穿、失效和容量；
- 队列、重试、乱序、重复、死信和背压；
- 并发控制、限流、超时、熔断和降级；
- 分片、复制、一致性、故障转移和灾备；
- 日志、指标、追踪、SLO 和容量规划；
- 输入验证、权限边界、密钥和审计。

升压时给明确 QPS、数据增长、读写比例、延迟目标、可用性、RPO/RTO 和成本约束；不要只说“流量很大”。

## 数据库

从一条实际查询或业务不变量出发：

1. 表/文档如何表达关系和约束；
2. 查询路径与索引为何匹配；
3. 并发更新和事务语义；
4. 执行计划、锁、热点和慢查询；
5. 在线迁移、回填、校验和回滚；
6. 分片、归档、合规和恢复。

能说出名词但不能预测具体查询、锁或失败行为，只算识别层。

## 网络与实时通信

从端到端需求而非协议背诵开始：

- 单向还是双向、消息频率、顺序和可靠性；
- 连接建立、认证、心跳、代理和资源限制；
- 断线检测、退避抖动、续传、去重和背压；
- HTTP 版本、多路复用、连接上限与队头阻塞；
- 消息 framing、增量解析和结构化数据边界；
- 可观测性、容量和服务端状态管理。

要求候选人走一次断线前后事件序列，避免只比较协议名称。

## AI 应用工程

按候选人实际使用深度选择：

- 消息与会话模型、上下文预算和历史压缩；
- 流式增量解析、结构化输出和取消；
- 工具调用状态机、权限、幂等和错误恢复；
- 检索、切分、召回、引用和评测；
- 模型选择、延迟、成本、缓存和降级；
- 提示注入、数据边界、日志脱敏和人工确认；
- 离线评测集、线上指标、回归和可观察失败。

“调用过模型接口”不等于设计过 AI 系统。先确认实际做过的范围，再扩展到新约束。

## 系统设计

### 校招/初级

重点看能否澄清需求，画出单机或简单服务的数据流，设计基本接口和数据模型，识别主要失败路径。

### 中级

要求容量估算、组件边界、并发一致性、缓存/队列、观测、发布和清晰取舍。

### 高级及以上

加入多租户、跨区域、迁移演进、SLO、成本、合规、组织边界和阶段性路线；要求说明决策何时应被推翻。

不要因为候选人画出更多框就给高分。每个组件都要对应约束、失败模式和运营成本。

## 可靠性与安全

可靠性追问：超时、重试、幂等、隔离、降级、恢复、容量、监控、演练和复盘。

安全追问：资产与信任边界、攻击面、最小权限、输入/输出处理、敏感数据、依赖供应链、审计和响应。

只考岗位相关的防御性工程判断，不要求攻击性演示。安全问题不能仅靠“加密”“白名单”一词通过，要说明保护什么、在哪一层、如何绕过以及如何验证。

## 协作与行为面

要求真实事件，并沿 STAR 继续追证：

- 当时目标和限制是什么；
- 候选人自己的行动，而不是“我们做了”；
- 如何处理分歧、坏消息、优先级和责任；
- 结果有什么外部证据；
- 下次会怎样改变。

高区分度主题：模糊需求、进度预警、线上故障、质量与期限冲突、跨团队依赖、错误复盘、带新人、技术债和拒绝不合理方案。

不要用家庭背景、人格测试或私人生活替代职业行为证据。

## 从对话推断潜力领域

不要问候选人想测哪个方向。持续从面试对话中收集信号，再选择最有信息量的方向：

- **项目纵深**：在哪类问题上能从实现继续讲到机制、边界和取舍。
- **主动关注**：会主动延伸、反问或追究哪些技术问题。
- **迁移基础**：哪些已有模型可以支撑进入相邻领域。
- **缺口性质**：当前卡点来自知识记忆、底层模型还是经验不足。
- **学习表现**：获得一个最小提示后，能否解释、自我修正并迁移。

优先选择与目标岗位相关、与现有基础相邻、尚未被项目经历直接覆盖的领域。潜力探测应依次观察无提示起点、最小提示吸收、相邻迁移和边界修正，不提前告诉候选人正在考察哪个领域，避免诱导表现。

结束后把领域潜力映射成技术路线：先修基础 → 核心机制 → 工程实践 → 可验证项目证据。每阶段给出优先级、产物、验收标准和暂不需要学习的内容。

## 区分缺口类型

边界出现后，用一次邻近探测判断：

- **记忆缺口**：忘了名称，但能从机制推导行为。
- **模型缺口**：无法预测最小例子的状态或时序。
- **执行缺口**：会解释原理，但无法形成接口、代码、实验或操作步骤。
- **证据缺口**：结论明确，但没有基线、测量或验证。
- **经验缺口**：知道理想方案，却说不出真实约束和事故处理。
- **表达缺口**：模型可能存在，但长期答非所问；重述后能否恢复是关键证据。

复盘时给出分类和依据，不笼统写“基础不扎实”。
