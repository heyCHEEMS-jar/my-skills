# 运营与批量生产手册

## 最小事件漏斗

命名可按产品调整，但语义保持稳定：

```text
landing_view
core_start
core_complete
result_view
share_click
invite_open
invite_complete
pay_intent
license_redeem
return_visit
```

不要收集完成判断不需要的个人信息。事件包含匿名产品版本、来源、时间和必要上下文即可；昵称、答案和订单信息与分析事件分开处理。

## 每周复盘顺序

1. **进入**：渠道带来多少有效访问，是否符合目标用户。
2. **开始**：用户是否在短时间理解价值并启动核心任务。
3. **完成**：步骤、性能、内容还是规则导致退出。
4. **分享**：结果是否值得发，分享接收者是否能立即理解。
5. **传播**：每个创建者带来多少新完成者，新用户是否再创建。
6. **付费**：谁在哪个时刻产生购买意图，兑换是否顺畅。
7. **回来**：产品是否存在每日、聚会、工作流或内容更新理由。

小样本直接写人数，如“20 人进入，8 人完成，1 人分享”，不要只写 40% 和 12.5%。

## 核心指标

根据产品类型选一个北极星指标：

- 社交游戏：每个有效房间带来的完成参与人数；
- 内容挑战：完成并分享的挑战数；
- 工具：成功产出并下载/复制的结果数；
- 创作者工具：每周有有效导出的活跃创作者数。

辅助指标包括创建率、完成率、分享率、邀请完成率、二次创建率、付费意向、兑换成功率、退款和客服量。

## 实验模板

```markdown
## 实验：<名称>

- 日期：
- 观察到的事实：
- 假设：
- 唯一主要变化：
- 目标用户/流量来源：
- 主要成功指标：
- 护栏指标：
- 最小样本或观察窗口：
- 结果：
- 结论：继续 / 转向 / 停止
- 后续：
```

一次实验只改变一个主要变量。修复明确故障不必伪装成增长实验，但要记录前后行为。

## 早期判断参考

阈值应在实验前根据渠道和产品设定。没有自己的基线时，可先把以下内容当作观察问题而非行业真理：

- 受邀用户是否能在无解释情况下完成；
- 每个创建者是否稳定带来多个参与者；
- 完成后是否有人主动再创建，而不是只礼貌点赞；
- 在展示付费权益前后，是否出现真实购买、询价或兑换；
- 客服成本是否会吃掉低价商品毛利。

达到预设样本仍无分享和付费信号时，先改变价值、场景或渠道，不继续增加题包和功能。

## 电商激活运营

商品页明确：

- 产品网址和支持的设备/浏览器；
- 免费体验和付费权益；
- 一个码可绑定的设备数；
- 当前版本买断、限时票或订阅的真实含义；
- 数据保存期限、更新和停止服务边界；
- 兑换前后的退款规则，以当期平台政策为准；
- 客服入口和常见故障处理。

监控从下单、发码、打开、兑换到成功使用的每一步。激活码共享严重时再增加账号或设备限制，不让少量盗用先伤害全部正常用户。

## 产品组合看板

每款产品只处于一个主要状态：

```text
Inbox → Research → Validate → Build → Beta → Selling → Scale / Hold / Stop
```

看板至少记录负责人、当前证据、最大假设、本周动作、成本、下一决策日期。限制同时处于 Build 的产品数量，默认一次只开发一款。

## 复用门槛

只有同一能力在至少两款真实产品中重复并且行为稳定后，才考虑提取公共模块。提取时记录：

- 两款产品真正相同的行为；
- 仍然不同的规则和数据；
- 公共模块的升级与回滚方式；
- 对资源占用、部署和故障面的影响。

复用目标是缩短下一款验证时间，不是建设一套看起来完整的平台。
