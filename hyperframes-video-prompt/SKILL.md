# HyperFrames 视频呈现与空间分镜提示词

把用户的主题整理成可直接制作的 HyperFrames 提示词，并单独交付旁白稿。用户本次要求优先，不复用其他视频的时长、数字、风格或路径。

先询问用户希望怎样呈现主题，不预设必须有角色或火柴人。重点在3D分镜构思、空间关系、动作与相机叙事，而不是固定2D版式的信息展示；这种构思思路不等于未经确认就把成片定为全3D。按用户选择采用角色演绎、物品叙事、空间动画、实拍、真实UI或混合形式；纯2D也以用户明确选择为准。

## 1. 制作前完整确认，不替用户做决定

先从对话提取用户已经明确给出的信息。凡是适用于本片、并会改变内容、观感、声音、素材或交付的参数，只要用户尚未说明，就主动询问并等待回复；不能擅自采用“常见配置”，也不能先生成提示词再把默认值写成备注。

### 完整制作确认清单

| 确认组 | 尚未明确时要问什么 |
| --- | --- |
| 内容目标与文案 | 想讲什么、观众是谁、知识基础、看完要记住什么、用途、文案语气或参考、需要怎样的结尾和必要声明 |
| 整体展现形式 | 开放询问希望怎样把主题呈现出来，有没有参考或不想要的形式；不要先假设火柴人、角色动画、实拍或UI教程 |
| 时长与发布 | 视频总时长、发布平台、**准确画面比例**；即使已知平台或用户只说“横屏/竖屏”，仍要询问 `16:9`、`9:16`、`1:1` 等具体比例 |
| 画布与交付 | 分辨率、帧率、输出格式、保存目录；只生成提示词还是实际制作与渲染；是否保留工程文件和独立字幕文件 |
| 背景与构图 | 纯黑画布、黑色立体舞台、其他纯色、场景化背景还是真实环境；构图极简还是丰富；不能默认使用黑幕或擅自添加地面 |
| 空间风格 | 纯2D、2.5D或全3D场景；物品的厚度、透视和空间层次需要多强；不能把2.5D自动理解为僵硬纸片动画 |
| 角色系统 | 仅在选定形式需要角色时问：希望什么形象、是否贯穿全片、数量、造型、颜色、表情与动作特征；选择火柴人后再确认线宽、轮廓与动作驱动 |
| 物品与材质 | 需要哪些具象物品；扁平、浅浮雕、纸雕或立体图形质感；倒角、阴影、反射与材质细节的强度；指定素材、品牌元素和禁用元素 |
| 动画与镜头 | 3D分镜与镜头语言的倾向、节奏、动作幅度、近中远景切换、推拉跟拍或空间绕拍、转场，以及眩晕、闪烁和运动模糊限制 |
| 光影与景深 | 是否需要地面接触阴影、环境光、轮廓光、景深与空气透视；希望克制图形感还是更强电影感 |
| 主视觉文字 | 要不要场景标题、关键数字、短标签或行动提示；文字固定还是随动作动态出现；字体、颜色和大致密度 |
| 配音、旁白与对白 | 是否需要人声；需要时确认是只写稿，还是还要生成/录制音频；采用真人或TTS、语言、人数、声音倾向、语速、情绪、停顿与角色分配 |
| 字幕 | 要不要字幕；需要时确认硬字幕或独立字幕、语言、字体、位置和样式；字幕与主视觉文字是两项不同决定 |
| 背景音乐 | 是否需要背景音乐；需要时确认风格、情绪、节奏、出现区间、音量倾向、是否循环，以及素材来源与版权限制 |
| 环境声与音效 | 是否需要环境声、动作音效、UI点击声或转场音效；需要时确认触发动作、真实或设计感、强弱、密度和禁用项 |
| 混音与音频交付 | 实际制作音频时，确认人声、音乐、环境声和音效的主次与压低关系，是否需要独立音轨，以及音频格式等交付要求 |
| UI 与外部素材 | 是否展示真实 UI、截图、Logo、图片、音频、视频或模型；确认文件位置、操作顺序、脱敏、授权状态与是否允许联网获取素材 |
| 工具与环境 | 现有HyperFrames项目、版本和运行环境；是否允许添加Three.js等依赖、使用或安装Blender；安装范围、离线限制、GPU条件、渲染时限，以及是否允许付费工具或云渲染 |
| 数据与合规 | 数据口径、公式、单位、来源、演示假设、免责声明和不能表达的承诺 |

### 声音确认规则

- 把配音/旁白、背景音乐、环境声和动作/UI/转场音效视为彼此独立的决定，逐项确认是否需要；用户只确认其中一项，不代表其他项自动启用。
- 用户没有说明声音方案时，先一次问清“是否需要配音或旁白、背景音乐、环境声、动作/UI/转场音效”，再只追问已选项目的必要细节，避免一开始堆砌音频参数。
- “需要旁白稿”不等于“需要制作配音音频”。需要人声时，明确区分只写稿、生成TTS、使用真人录音或等待用户提供音频；未获授权时不能声称已生成或录制。
- 有多种声音时确认主次：通常先保证人声清楚，再按用户偏好安排音乐压低、环境声铺底和关键动作音效；静音段、卡点和声音转场也要服务叙事，不能用密集音效掩盖画面问题。
- 需要外部音乐、音效库、真人配音、付费TTS或上传音频时，继续确认素材来源、版权、费用、联网与隐私边界。只交付提示词时写清待制作要求，不虚构素材或产物。

### 询问规则

- 用户已经明确给出的项目不重复询问，其余适用项要分批问完，不能因为问题较多就自行补齐。
- 每轮最多询问四组相关事项，把同组的小问题合并成一句清楚的问题；回答后继续下一组，直到完整确认。
- 优先开放询问内容目标与整体展现形式，再确认时长、平台与准确比例、背景和空间倾向；根据形式继续询问角色或对象、镜头、文字、声音、素材、工具和交付。
- 默认用开放式问题，让用户描述偏好、参考和禁用项。需要辅助说明时提供少量方向性例子，不把例子当成封闭菜单。
- 不用“白色火柴人+橙色道具+黑幕+快节奏”这类捆绑套餐代替询问。选项若有必要，按一个决策维度泛化，允许用户自由描述、组合或指定其他形式；用户没有选的附带参数继续确认。
- 不适用的项目跳过，例如无角色就不问骨骼，无旁白就不问音色，无字幕就不问字幕位置；完整确认不是把所有问题机械问一遍。
- **准确比例必须主动确认。**“抖音”“短视频”“竖屏”都不能自动等同于 `9:16`；“B站”“横屏”也不能自动等同于 `16:9`。
- **背景与空间风格必须主动确认。**纯黑画布与黑色立体舞台是不同选择；纯2D、2.5D、3D场景也不能互相代选。可以推荐，但未经同意不采用。
- **线条外观、动作驱动与分镜维度分别确认。**不能因角色由线条组成就默认固定侧视或平面场景。用易懂的问题确认空间镜头和转身、负重、攀爬等需求，不要求用户自己设计骨骼或选IK算法。
- **工具和资源边界必须问清。**没有给出具体库名不代表只能用原生代码；允许按需引库也不等于允许付费、云上传、任意安装范围或未经授权下载素材。
- 已获用户明确授权的实现选型在该边界内自行决定，不逐个API或包名反复询问；超出安装、素材、费用、外部服务或渲染预算边界时先询问。
- 如果只缺“是否加字幕”或“具体比例”，就只问缺少的事项，不重开完整问卷。
- 可以给出一项有理由的推荐，但必须让用户确认，不能把推荐直接写成已决定的参数。
- 用户明确说“你决定”“全部按你的推荐”或逐项授权代选时，才替用户选择；“随便”“都行”含义不清时，先确认是否授权代选。
- 全部适用项确认后，先用简短清单复述最终制作参数并请用户确认；得到确认后才能生成最终 HyperFrames 提示词和旁白文件。用户明确要求跳过最终复述、直接按已给参数执行时除外。
- 每轮把回答记入制作参数清单，区分“已确认”“明确授权代选”“不适用”和“待确认”。不要把推荐、历史成片配置或自己的推断记成用户回答。
- 在完成必要确认前，只能整理事实、核对数据、检查素材或只读查看环境，不能安装制作依赖、启动渲染或创建最终交付文件。
- 修改已有视频时保留已经确认且未受影响的设置，只问此次变化牵涉的事项；用户只是优化本Skill时，更新通用规则，不重新询问或重做某一条视频。

整体形式、角色和技术均以用户确认优先。无角色时由物品、环境、镜头或真实操作反馈推进；不强行加火柴人，也不因默认样例改变用户指定的风格。

## 2. 确认后先组织故事与3D分镜，再组织信息

先构思可被相机观察的空间与行动，再编排数字和文字。分镜的主干是角色的位置、路径、接触、环境变化和观察角度，不是几张固定版式的信息卡。

1. 先确定观众看完应记住的一句话，再按时长取舍内容。
2. 根据展现形式确定贯穿对象、目标和变化主线。对象可以是角色、物品、空间或操作流程；知识点成为可见事件与因果结果，而不是必须给火柴人安排一个任务。
3. 核实公式、数字和时效事实；演示假设和不确定性必须说清，不能包装成保证。
4. 先写旁白并校验自然朗读时长。让有效讲述覆盖大部分成片，只保留必要换气；过长时删减重复内容，不靠异常加速硬塞。
5. 根据旁白、空间动作和镜头变化分配时间。时间轴从零连续覆盖总时长 `D`，最后一个时间点严格等于 `D`，无空档、无逐帧提示词。没有旁白时由动作的可理解节奏决定时长。
6. 每段先写“空间起点 → 角色或对象变化 → 相机观察 → 可见结果 → 下一段出口”。短视频减少支线与场景；长视频保留同一角色、物品或空间线索接力。
7. 参考具体作品时只提炼角色形态、材质、镜头、节奏、色彩和信息密度，不复制可识别画面，也不冒充创作者。

### 文案：通俗易懂，但不写成过度大白话

默认在易懂与准确之间取平衡，再按用户确认的受众、语气和参考调整。内容要像清楚的解释，而不是论文摘要、聊天碎句或营销口号。

- 用具体对象、常见动作和清楚的因果表达概念，先讲要点，再补必要推导和限制；不靠抽象名词堆砌制造专业感。
- 必要术语保留并在首次出现时简短解释，例如“月净储蓄，就是扣除必要支出后，能够稳定留下的钱”。不能为了易懂把复利说成稳赚，或删除假设条件。
- 句子适合自然朗读，长句拆开，指代明确；不过分正式，也不频繁使用语气词、网络梗、方言、甩段子或刻意亲昵的称呼。
- 避免“轻松逆袭”“一个方法搞定”“钱自己生钱”等夸张承诺和套话；不训诫观众，也不虚构观众的心理活动。
- 旁白解释原因、推导、限制和行动，画面展示关系与变化。必要数字要说清，但不逐句照念场景大字，不把同一结论反复换词扩写。
- 收尾给明确、适度的行动提示，不硬凑金句、鸡汤或机械总结。事实限定应融入清楚的解释，而不是用小字掩盖误导。

语气校准例子，只示范表达方式，不复用到每个主题：

- 太抽象：“目标资本形成周期取决于可持续现金流盈余。” → 平衡：“存到目标金额，主要取决于每月能够稳定留下多少钱。”
- 太口水：“想搞钱就得猛省，省着省着钱就多了。” → 平衡：“先算清可持续的月结余，再考虑怎样增加收入、调整支出。”

## 3. 按展现形式设计3D分镜与叙事动作

### 先做空间调度，不把分镜锁死成平面视图

- 在用户确认的空间风格下，先确定舞台结构、角色与道具的前后/左右/高低位置、动作路径和相机观察方式。优先用3D场景思维构思，不从一张固定侧视画布开始填图标。
- 每段要有可感知的空间事件，例如角色从近景进入后景、绕过道具、穿门、上下台阶、把物品从台面搬到地面，或相机改变观察角度揭示原先被遮挡的结果。
- 景别和视角随叙事改变：近景展示接触与细节，中景展示身体动作，远景交代距离和环境；低机位、俯视、四分之三角度、推拉与跟拍在有解释价值时使用。
- 相机运动必须有目的。不要全程固定侧视，也不要全程绕圈；文字需要阅读或关键动作需要看清时允许镜头停稳。
- 2.5D可以使用三维场景、空间线条、立体物品和受控光影，再以图形风格呈现；不是把2D图片旋转一下或加一道投影。按用户确认的纯2D要求制作时例外，不强行升级。
- 先写清动作和空间因果，再决定是否需要数字标签。不能用更厚的图标、更多装饰或一条绕拍镜头掩盖没有构思的分镜。
- 例：角色从前景蹲下抓住硬币，转身沿斜向道路走向后景金库；相机侧向跟随并逐渐拉远揭示距离，抵达后推近手与仓门的接触。不是“人物站左边，数字放右边”。例子只示范设计方式，不复用到所有主题。

### 按需建立角色或叙事对象系统

用户选择角色形式时，在主提示词中给出简短设定；无角色时定义贯穿物品、环境或操作对象，不强行添加人物：

- **主角**：固定轮廓、比例、线宽和主识别色；不能每段换成不相干的新人物。
- **配角**：只在确有对照、协作或冲突时加入，用发型、帽子、服装块或随身物区分，避免堆角色。
- **表演方式**：通过走、拿、推、拉、搭建、拆除、选择、失败、重试和观察结果表达含义，不依赖复杂嘴型或大段对话框。
- **物品系统**：选择与主题相关、观众一眼能理解的物品，让物品在前后段重复出现并发生变化，而不是每个知识点临时换一套图标。

用户要求“全程有某角色”时，每个时间段保持该角色的行动与因果连续。允许物品、数字或UI特写，但需通过手、光标、视线、影子、前后动作或反应接回角色。用户选择无角色时，用对象变化、空间运动和真实操作反馈保持连续，不必为了此规则额外添加人物。

### 选择火柴人时：线条外观与骨骼驱动分开设计

选用火柴人时，头部、躯干、四肢和手脚按线条或曲线绘制。线宽、圆角、颜色和轮廓遵循用户确认；不能为了“3D动作”改成球形头、圆柱肢体、胶囊人或塑料玩偶。

- **线条是最终外观，骨骼是内部控制。**可以使用二维分段关节，也可以使用3D骨骼或空间关节坐标，再将结果投影或绘制为空间线条。使用3D骨骼不意味着必须渲染实体皮肤或管状四肢。
- 用户选择3D骨骼驱动时，建立适用于动作的根节点、骨盆、脊柱、胸腔、头部及肩肘腕、髋膝踝链条，允许躯干扭转与正面、侧面、四分之三朝向变化。
- 根据动作使用IK/FK：搬运、推拉、攀爬时固定手脚接触点；跑步、转身和挥动时用自然关节弧线衔接。保持肘膝弯曲方向合理，过渡连续。
- 脚掌在支撑阶段锁定接地点，抓取时手的位置跟随物品。需要阴影或遮挡时可用不可见代理辅助，但最终画面仍然只显示线条角色。
- 每个主要动作写清视线先行、动作预备、重心转移、发力、接触、缓冲和余势。例如搬物不是整个人平移，而是先屈膝抓稳，再用腿和骨盆起身，肩肘随重量调整。
- 禁止脚滑、手部脱离道具、关节反折、穿模、躯干不受力、整个人刚性平移和无过渡的姿势跳变。
- 用户明确选择纯2D时，仍通过分段关节、动作弧线和受力反馈保持灵活；不能自行升级成3D场景。画面维度与肢体灵活度不是同一项限制。

### 根据确认的风格增加空间层次

2.5D是一种视觉呈现，不等于“几张平面图上下移动”。角色仍按线条绘制，空间感可以来自物品与场景，而不是把角色实体化。

- 用户选择2.5D时，按需为物品加入浅厚度、倒角、侧面明暗和接触阴影；保持主题需要的图形风格，不强行做写实商品。
- 把动作对象放在明确的空间位置，利用Z轴分层、遮挡、透视、视差、尺度和镜头距离展示关系；不要把所有对象贴在同一平面。
- 按已确认背景选择地面、台阶、门框、工作台或道路等空间锚点。选择黑色立体舞台时可以有暗色地面与软影；选择纯黑画布时不能擅自改成舞台。
- 根据用户选择加入环境光、轮廓光、景深和空气透视。线条角色、当前动作和关键文字必须清楚，不能把“高级感”做成看不清的暗画面或频繁抽焦。
- 镜头推拉、跟拍和小幅绕拍用于揭示动作、物品厚度和前后关系，不做与叙事无关的360度旋转。场景文字可随物体定位，但读字时要停稳且避免强透视变形。
- 简单构图不等于简陋：保留必要的形状细节、接触反馈、空间位置和光影统一性；不靠添加指标面板、随机装饰或粒子填满画面。

### 按用户确认的背景组织构图

背景形式必须来自制作前确认，不能自动决定。以下只适用于用户选择纯黑画布的情况；黑色立体舞台按上面的空间风格规则制作，不混为一谈。用户选择纯黑画布时：

- 使用用户确认的黑色底色、主体颜色与留白密度，确保对象清楚；不自行指定白色角色或强调色，也不擅自加入渐变面板、发光边框或科技UI。
- 构图保持简单，但不能空洞。用角色姿态、物品形变、大小关系、遮挡、景深、路径和镜头距离建立层次，不靠装饰性卡片填满画面。
- 每一时刻只突出当前动作所需的少量角色、物品和文字，让观众先看懂动作，再看到结果。
- 场景变化主要来自角色移动、物品进入与退出、尺度变化和动作接力；黑幕本身保持稳定，避免每段换一张“背景模板”。
- 简单构图不等于静止。角色重心、四肢、道具反馈、运动轨迹、镜头跟随和声音卡点都要配合，让动作具有准备、发生、受力和结果。

用户选择其他纯色、场景化背景或真实环境时，沿用同样的行动优先原则，并按已确认风格控制信息密度。

### 每段都写清行动与空间信息

时间轴中的每一段都要明确：

1. **叙事对象是谁**：角色、物品、环境或操作对象是什么；无角色形式不额外添加人物。
2. **为什么行动**：这一段要解决什么问题或完成什么目标。
3. **具体动作或变化**：角色如何行动，或对象与环境如何变化；不能只出现一张数字卡。
4. **使用什么物品**：物品怎样被拿起、移动、组合、消耗或改变。
5. **产生什么结果**：环境、物品、角色状态或空间关系怎样变化。
6. **相机为什么这样看**：起止机位、景别、运动路径、关注对象，以及如何让空间关系和接触动作可读。
7. **怎样接到下一段**：空间出口、角色运动、物品传递或形变、遮挡和视线如何接力。

选择角色演绎时，角色不能只是装饰；删掉角色后如果仍是一套完整看板，说明没有落实演绎。选择无角色时，对象和镜头的可见变化也不能退化为静态信息卡。

### 把抽象信息转成可见事件

优先从信息的含义选择动作，不机械套用固定隐喻：

| 信息任务 | 优先演绎方式 | 避免 |
| --- | --- | --- |
| 数量与积累 | 角色搬运、堆叠、装满容器、走过里程或翻动日历 | KPI 卡片、单独的大数字翻牌 |
| 大小与差距 | 相同角色在不同距离、重量、高度或物品数量下完成同一任务 | 并排柱状图占满画面 |
| 时间变化 | 角色和场景随季节、年龄、路程或物品磨损逐步变化 | 折线图成为主镜头 |
| 流程与步骤 | 角色携带同一物品通过连续站点，每站完成一个动作 | 流程框和箭头逐项亮起 |
| 因果关系 | 先展示动作，再让机制可见，最后出现结果和角色反应 | 先抛结论，再展示说明卡 |
| 选择与权衡 | 角色在岔路、天平、有限背包或资源分配中做决定 | 优缺点表格或雷达图 |
| 软件操作 | 火柴人在设备场景中操作真实 UI，操作后由场景或物品呈现结果 | 无角色的长时间录屏或虚构看板 |

这些是转换思路，不是必须重复使用的素材库。每条视频根据主题选择自己的角色、物品和空间关系，避免所有成片都变成金币、管道和进度条。

### 让数字与文字跟随动作，而不是占住版式

- 主视觉文字是否出现、出现多少以及采用固定或动态方式，必须来自制作前确认；时间轴不要求每个场景都配置标题。
- 用户选择动态文字时，每条文字都写清**触发、入场、短暂停留和退出**：由角色动作或物品变化触发，在动作附近出现，读清后随物品移动、被角色带走、变形成下一件物品或自然退出。
- 文字位置由当前构图和因果关系决定，可以出现在角色手边、物品表面、道路旁、上方留白或动作终点，不能机械固定在每段顶部、左上角或同一张标题栏里。
- 位置灵活不等于随机漂浮。文字要与角色视线、手势、物品或运动轨迹建立可见关系；进入位置、停留位置和退出方向必须稳定复现。
- 文字运动期间保证可读：入场后短暂停稳，避免读字时持续旋转、抖动或高速移动；同一时刻只保留当前动作必需的信息。
- 数字应附着在角色拿取的物品、走过的路标、日历、秤、容器刻度或操作结果旁，作为动作证据，而不是自己成为整段画面。
- 字幕与主视觉文字分开处理。用户选择字幕时，字幕放在稳定安全区，不跟随场景乱跑；动态标签主动避开字幕、角色脸部和真实 UI 的关键区域。
- 固定场景标题只在用户明确要求时使用，也不默认每段重复同一标题模板。没有必要的场景可以完全不放主视觉文字，让动作和旁白承担信息。
- 非 UI 主题默认不生成仪表盘、指标卡、数据表、筛选器、网页面板或整屏图表。
- 精确关系确实无法只靠演绎表达时，可以让角色短暂展开纸张、黑板或场景内示意图，并亲自指向、移动或修改它；读完后立即回到行动，不让示意图接管叙事。
- 任何数据标注都要保持单位、基线和口径准确，不能为了形象化扭曲比例或因果。

## 4. 软件与产品教程：按确认的形式结合真实UI

当 UI 本身就是教学对象或证据时，不把它强行改造成抽象道具：

1. 优先使用用户提供或已核实的真实界面、真实字段和真实操作顺序；没有可靠素材时明确需要占位界面，不能虚构成真实产品功能。
2. 需要角色时让用户选定的角色在设备场景中实际操作；不要默认加火柴人。无角色时由真实光标、触控、设备镜头和操作反馈推进步骤。
3. 需要看清步骤时可以推近真实UI，同时保留光标、触控、手或按所选形式呈现的反馈；角色仅在用户选择角色形式时出现。界面可读性不能被空间镜头牺牲。
4. 每次界面操作都要产生可见后果：状态变化、物品出现、路径打开、问题解决或角色行为改变。不要只让按钮高亮后进入下一张截图。
5. UI 可读性高于角色遮挡效果。角色和道具不得压住关键按钮、代码、字段、错误信息或字幕。
6. 操作完成后按已确认形式，用设备、结果物品、镜头或角色动作连接下一步骤，不为了场景模板额外加人物或卡片。

若视频不是软件或产品教程，UI 只能作为必要的小道具，不能为了“科技感”自行添加数据大屏、手机面板或假仪表盘。

## 5. 连续动作链与平滑过渡，不做摆姿势的木偶分镜

每段是一个随时间展开的事件，不是一张角色姿势图。动画覆盖开场、段内、转场和片尾；不能只给每个场景摆一个动作，再靠切换场景维持视频长度。

### 段内要持续发生事情

- 为每段写清“进入与预备 → 行动展开 → 受力或条件变化 → 结果与反应 → 接出下一段”的动作进程，按时长和内容分配，不写死动作数量或事件间隔。
- 姿势是动作中的关键节点，不是整段画面的终点。使用角色时，身体、重心、关节、视线、手脚接触和道具持续配合；不能只摆姿势、挥手、点头或整个人平移。
- 无角色时，由物品运动、展开、搭建、组合、形变、机制运行、环境变化或真实操作反馈形成连续事件，而不是把静态道具逐张替换。
- 连续运动要推动信息：每一次搬运产生积累，每一次接触带来反馈，每一次选择改变路径。重复动作可以用于表现过程，但状态和结果必须随之推进。
- 镜头随动作观察空间，不能只推近、摇移或绕拍一个不变的姿势。景别变化与角度变化是叙事动作的观察方式，不是代替角色或物品动画的补丁。
- 关键数字需要阅读时允许文字和相机停稳，但动作链中的另一层继续有意义地变化；自然停顿应短且有目的，不靠无意义呼吸、抖字、灯光闪烁或粒子维持“动态”。

### 段间要接住运动，不只是切换

- 每个转场写清上一段哪个对象、动作、路径或空间出口接到下一段，以及下一段怎样接住它；角色、物品或机制至少有一个明确的视觉接力点。
- 优先使用物品传递、动作匹配、沿路径跟随、遮挡穿越、空间穿门、形变或镜头连续行进。旧场景退出与新场景进入要有时序，不是整幅画面突然替换。
- 交接时保持合理的位置、朝向、速度、受力和视线连续，缓入缓出自然；IK接触、关节过渡和物品约束不能在场景边界突然跳变。
- 不用黑场、连续淡入淡出、静态卡片切换或每段重新摆一个姿势作为默认转场。即使需要切镜头，也要保持动作与空间关系连贯，切换不是全部动画。
- 开场直接进入动作，结尾从仍在进行的动作自然收束，不为片头或片尾额外冻结成长时间封面。
- 全部动作、相机、文字、场景状态和声音由可seek主时间轴驱动；跳转到转场前后也应得到连续、可复现的画面。

平静、极简或商务风可以降低运动幅度，但不降低动作的完整性。简单构图不能成为静止、木偶姿态或敷衍分镜的理由。

## 6. 按需使用3D库或Blender，不限制实现手段

确认视觉目标和工具边界后，再选择实现方式。不要因为提示词面向HyperFrames，就假设只能用原生CSS、SVG平移或少量内置动效；也不要把某个库当作每条视频必装依赖。

- 在已获授权的范围内，可自行选择Three.js、其他合适的3D库、动画或IK工具；需要建模、绑定、动作烘焙或离线渲染时，也可以使用Blender。
- 库名与工具只是实现手段。主提示词应同时写清可见效果和实现要求，例如“3D关节驱动线条火柴人，物品有厚度与接触阴影”，不能只写“使用Three.js”就当作已经设计好动画。
- 实际制作前检查目标项目、依赖版本、渲染环境、工具是否安装、格式与合成链路是否兼容。不要把未核实的包、IK组件或Blender集成说成HyperFrames内置能力。
- Three.js等实时方案可在3D场景中求解关节、绘制线条、布置物品和相机；线宽、遮挡、光影和导出结果必须在实际环境验证。
- Blender方案可制作线条/曲线角色、绑定动作、物品和场景，按需要导出动画数据或渲染素材，再由支持的合成链路接入HyperFrames主时间轴。
- 需要安装时使用已确认的范围，优先项目级依赖；安装Blender、下载大体积资源、付费、云渲染或把素材传至外部服务等超出既有授权的操作，必须先询问。不能用“引入库”绕过权限、费用或素材授权边界。
- 物理、IK、角色动作、相机和音画同步都由主时间轴的绝对时间驱动。需要模拟时先烘焙或固定初态与步长，保证跳转到任意时间、重新播放和重新导出能得到相同结果。
- 工具不可用或效果受限时，说明具体阻碍与可选办法并让用户决定；不能悄悄把已确认的灵活动作退化成僵硬纸片，或把2.5D降成纯2D。
- 只交付提示词时，注明待制作端检查的技术条件，不谎称已安装、已绑定或已渲染。实际制作时先检查关键动作和渲染片段，再制作全片。

## 7. 交付提示词与按需旁白 Markdown

### `[主题]-HyperFrames提示词.md`

给出一个可直接复制给HyperFrames的完整提示词。目标是成片时，要求制作端完成创建与渲染而非只返回方案；本次只要求文档时不要自行执行安装或渲染。按需要包含：

1. 用户最终确认的制作参数表：内容、整体展现形式、时长、准确比例、背景、空间风格、角色或对象、动作、文字、声音、素材、工具授权、交付和保存设置。
2. 核心结论、数据口径、素材与必要免责声明。
3. 3D分镜与空间调度、贯穿对象、物品与材质；需要角色时写造型和关节/接触规则，选择火柴人时明确线条绘制，不默认人物或体积肢体。
4. 动作设计、镜头与光影、动态文字、UI边界、转场、实现工具和确定性时间轴；不支持或尚待核实的能力明确列出。
5. 连续时间轴：每段的叙事对象、目标、起始空间、段内动作进程、接触与反馈、状态推进、结果、相机起止位置与景别、接出对象及下一段如何接住、文字的触发与退出、按需旁白和声音。不把一个关键姿势当作整段分镜。
6. 验收：展现形式、时长与比例、空间分镜、按需角色外观与关节接触、动态文字、真实UI、静帧、数据、声音、seek一致性和导出结果。

### `[主题]-普通话旁白.md`

单独整理：

- 总时长、声音、语速和停顿要求。
- 带起止时间的分段旁白。
- 去掉时间码与制作说明的连续朗读稿，方便配音或 TTS。

需要旁白时，两份文档中的分段与连续朗读稿必须逐字一致，时间段连续覆盖总时长；旁白文件不混入角色、物品、UI、镜头和转场指令。用户确认无旁白时，主提示词明确禁用，不虚构配音稿；用户只要提示词时不强制创建旁白文件。语言与文件命名遵循本次确认。

## 8. 保存与验收

用户指定目录时，以UTF-8保存已确认的交付文件；文件名使用本次主题并避开非法字符。写入前检查同名文件并确认覆盖或另存，不默认覆盖。需要旁白时两份Markdown清楚分开；无旁白或只要提示词时不强制创建第二份文件。

交付前检查：

- 先开放询问整体展现形式，所有适用制作参数能追溯到用户回答或明确代选授权；准确比例、背景、空间风格、角色与工具边界不根据题材或模板自行决定。
- 生成前已经向用户复述最终确认清单；主提示词中的时长、比例、背景、角色、文字、声音、素材和交付设置与清单一致。
- 用户选择不要配音/旁白、字幕、主视觉文字、背景音乐、环境声、动作/UI/转场音效或 UI 画面时，主提示词明确禁用对应内容，不能因为模板习惯又加回来。
- 只使用本次变量，没有残留示例时长、数字、角色、风格或路径。
- 时间轴连续且结束时间等于总时长。
- 每段有叙事目标、动作或对象变化、结果和视觉接力；角色、物品、环境或真实操作反馈与所选展现形式一致。
